# Pending / unsolved

Known gaps, why they're not done, and what finishing them would involve.
Kept here rather than in commit messages so it survives.

---

## 1. Purchases can't be edited or deleted

**Status today**

| Document | View | Edit | Delete |
|---|---|---|---|
| Bill (water) / Sale | yes | yes | yes — refused while a receipt exists against it |
| Payment / Cash receipt | yes | yes | yes |
| Voucher (expense, income, contra, withdrawal, deposit) | yes | yes | yes |
| Donation | yes | yes | yes |
| **Purchase** | yes | **no** | **no** |

Everything except a purchase can now be corrected in place.

**Why a purchase is harder than the rest**

Every other document writes to one place — the ledger. A purchase writes to
**two**: ledger entries *and* inventory movements (stock in). That second leg is
what makes it difficult:

1. **The stock may already be gone.** If 50 pipes were bought and 30 have since
   been issued to a job, unwinding the purchase would leave stock at −30 or
   orphan the issues that consumed it. The system has to check that nothing from
   this purchase has moved before it can be touched.
2. **Cost flows forward.** Item cost is derived from what was paid. Changing a
   purchase price retroactively changes the cost of every issue made after it —
   so an edit isn't one correction, it's a recalculation cascade through
   everything downstream.
3. **Partial payment.** A purchase can be partly paid. Editing the total has to
   reconcile against what's already been paid out.

**What finishing it looks like**

An `edit_purchase()` / `delete_purchase()` RPC on the same pattern as
`edit_voucher()` (migration 175): refuse when any stock from the purchase has
been issued, refuse when payments exist against it, then reverse both the ledger
leg and the inventory leg and re-post. Same transaction, same audit row.

## 2. How professional accounting software handles this — and how we differ

Worth knowing, because our approach is a deliberate departure.

**Real systems mostly do not let you edit or delete a posted document.**
QuickBooks, Xero, Odoo, SAP all treat a posted entry as immutable. Corrections
happen one of three ways:

- **Reversing entry (contra entry)** — the standard. Post an equal-and-opposite
  entry, then post the corrected document. Both stay visible forever. The books
  show the mistake *and* the fix, which is exactly what an auditor wants.
- **Void** — keep the document and its number, zero its amounts, mark it VOID,
  issue a replacement. The number is never reused and never disappears: **a gap
  in a numbered sequence is a red flag**, since it's indistinguishable from a
  document someone destroyed.
- **Credit note / debit note** — for sales and purchases you don't edit the
  invoice at all, you raise a credit note against it.

They also apply **period locking**: once a month or year is closed, nothing
inside it can change at all. Edits are only possible in the open period.

**What we do instead**, and why:

We allow real edits and real deletes, with `audit_log` capturing the full
before-image of every change (and, for deletes, enough to restore the row). For
a village committee this is the right trade: the people entering data are
volunteers, typos are frequent, there's no external auditor, and asking someone
to post a reversing entry to fix a digit would mean it simply never gets fixed.

**But be clear about the cost.** Our receipt/voucher numbers come from a counter,
so deleting a document leaves a permanent gap in the sequence, and the ledger no
longer shows that anything was ever there — only `audit_log` does. If the
committee ever faces a real external audit, or grows past the point where
everyone trusts everyone, the honest upgrade path is:

1. Add `status = 'void'` to bills/vouchers/payments and void instead of delete.
2. Lock closed months (there's already a monthly-closing report to hang this on).
3. Switch corrections to reversing entries, keeping delete for drafts only.

None of that is urgent today. It's the direction to go if the committee grows.

## 3. Voucher edit — deliberate refusals

`edit_voucher()` (migration 175) refuses in four cases, each on purpose:

- **Not `posted`** — a voucher in the approval queue was submitted at a specific
  amount; changing it under the approvers would defeat the approval gate.
- **Has itemised lines** (`voucher_line_items`) — the header total is derived
  from the lines, so editing the header alone would put them out of step. These
  need editing from the voucher form, which does not currently support loading
  an existing multi-line voucher back into it. **That's a real gap.**
- **Generated by another document** — a bill's security deposit or waiver, a
  connection charge, a payslip recognition, a settlement. Editing it here would
  leave the parent document describing something that no longer matches.
- Same account on both sides, zero/negative amount, or accounts from the other
  system.

## 4. Volunteers and publishers — what was built, and what wasn't

Built: an admin Volunteers page (there was none — offers could be made but never
accepted), notifications on both sides of Get Involved, `project_tasks` for
giving volunteers work, structured "how can you help" questions on signup,
templated accept/decline replies, and a versioned Publisher content-rules gate.

Still open:

- **Get Involved and My Volunteering still overlap.** The first writes to
  `suggestions`, the second to `volunteers`. A resident who fills in Get
  Involved reasonably believes they have volunteered, but nothing appears under
  My Volunteering and neither page mentions the other. Needs a pointer between
  them, or merging the two flows.
- **Accepting a publisher does not create the account.** By design — an account
  arrives through Users → invite so the person sets their own password, and a
  password must never be sent in a notification. But it is a manual second step
  that is easy to forget after clicking Accept.
- **Volunteer replies still don't send.** Same root cause as everywhere else:
  the reply queues into `notifications_log` and there is no WhatsApp API. The
  portal notification does arrive; the WhatsApp message does not.
- **Content types remain separate where they should be.** `news_posts` (with
  categories, now including Editorial and Poetry), `video_content`,
  `gallery_albums`/`gallery_items` and `news_ticker` are four different shapes,
  and merging them would be tidiness for its own sake. Only articles were
  consolidated. If a fifth *article-like* type is ever wanted, it is a row in
  `post_categories`, not a new table.

## 5. Recurring schedules depend on pg_cron actually being enabled

Migration 015 tried `CREATE EXTENSION pg_cron` + `cron.schedule(...)` inside an
exception handler that swallowed any failure, so nobody could tell afterwards
whether it worked. On Supabase, pg_cron normally has to be enabled from the
dashboard (Database > Extensions) — a migration cannot force it.

If it is NOT enabled, the only thing that runs schedules is a staff member
opening the admin Recurring page, which calls `run_due_recurring_schedules()`.
That is a safety net, not a mechanism: nobody should have to remember to open a
page for bills to exist.

`recurring_scheduler_status()` (migration 185) reports the truth — whether the
extension is installed, whether the job exists, and its cron expression. Call it
before assuming schedules are automatic.

## 6. Security: the whole ledger was public (fixed in 182)

Recorded because the cause is subtle and could easily be reintroduced.

Measured with the **anon key** — the one shipped in every browser bundle:
`ledger_entries` 244/244, `bills` 38/38, `payments` 34/34, `vouchers` 10/10,
`consumers` 12/12 (names, mobiles, addresses). Only `donors` was safe.

**Cause:** migrations 002/007/009 created `FOR SELECT USING (true)` policies.
The RBAC work in 014 added strict policies *alongside* them. **Postgres OR's RLS
policies together**, so adding a strict policy next to an open one restricts
nothing at all. Migration 116 noticed this for `donors` and dropped
`public_read_donors`; the other five were never revisited.

**The rule to remember:** adding a policy can only ever grant more access. To
restrict, the permissive policy must be *dropped*.

Supabase's advisor did not catch this. It flagged the five `*_public`
SECURITY DEFINER views as Critical — which are the *correct* pattern, narrow
projections that deliberately read past RLS to expose only safe columns — and
said nothing about five tables with no protection at all. After 182 the advisor
will show **more** such warnings, not fewer, because the fix adds two more of
those views. That is expected; dismiss them.

Also note the public bill lookup now requires two factors (consumer number plus
last four digits of the registered mobile, or house number), because consumer
numbers are sequential and a lookup on that alone is an enumeration oracle. A
wrong verifier and an unknown consumer number return the same empty result on
purpose.

## 7. Other known gaps

- **iPhone 7 / iOS 15 cannot run the site.** Tailwind v4 emits `@property` and
  `color-mix()` and requires Safari 16.4+ *by design*; its PostCSS plugin exposes
  no browser target, and Lightning CSS can't downlevel either. Options are: accept
  it, hand-write CSS fallbacks (~1 hour, partial), or downgrade to Tailwind v3
  (multi-hour, high regression risk). Undecided.
- **Thermal printing is layout-only.** The slip renders at 302px (58mm) and
  exports as an image. Direct ESC-POS command output to a Bluetooth printer is
  not wired, and 80mm paper width has never been tested on real hardware.
- **Links die in shared PNG/JPG.** Images have no way to store a hyperlink. PDFs
  now carry real link annotations (though WhatsApp's built-in PDF viewer often
  ignores them — opening in a real PDF reader works). A QR code would solve it
  for images; declined for now.
- **WhatsApp attachment on desktop.** Mobile attaches the file directly via the
  OS share sheet. Desktop cannot — `wa.me` accepts text only and no browser API
  can put a file into another site's composer. Current fallback copies the image
  to the clipboard so it's one paste away.
- **Payment screenshots are never cleaned up.** Deleting a donation leaves its
  file behind in the private `donation_receipts` bucket, orphaned. Not a leak —
  the bucket is not public-read — but it accumulates, and a "deleted" donation's
  screenshot still physically exists. Needs a storage delete alongside the row
  delete, or a periodic sweep.
- **"Awaiting confirmation" money appears in neither receipt total.** The donor
  receipt's *Total Contributed* counts verified donations and *Announced
  Remaining* counts pledges, so a donation that is paid-but-unconfirmed shows in
  neither. Defensible (unconfirmed money should not be claimed as either), but a
  donor in that state sees no figure reflecting their payment.
- **Test data still in the database** — see the counts in the delete-scope
  discussion: 2 `__TEST__` donors, 1 `__TEST_BPC_` consumer, 4 `Test Proposer*`
  portal users, 45 of 54 donor accounts matching test patterns, plus 8 demo
  donors and 10 demo consumers carrying 38 bills / 34 payments / 241 ledger
  entries. To be cleared before the real donor database is uploaded.
- **Stray macOS duplicate files** in the working tree (`.next 2/`,
  `Header 2.tsx`, `docTranslations 2.ts`) — stale copies, deliberately not
  committed, safe to delete.

## `REVOKE ... FROM PUBLIC` has never kept `anon` out (codebase-wide)

**37 migrations** end their function definitions with

```sql
REVOKE ALL ON FUNCTION some_fn(...) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION some_fn(...) TO authenticated;
```

and **none** of them revoke from `anon`. This does not do what it reads as.
Supabase ships

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role;
```

so every new function is granted to `anon` **explicitly, by name**, and
revoking from `PUBLIC` does not remove an explicit role grant. Confirmed
empirically with the anon key: functions "revoked from PUBLIC" are still
callable by a signed-out visitor.

**This is not currently a breach.** Every one of these functions guards itself
internally, and `auth.uid()` is NULL for anon, so the permission checks refuse
and the SECURITY DEFINER bodies return nothing. The defence in depth is what is
actually holding. But the grant is not the barrier it was written to be, so the
internal guard is the *only* barrier — and migration 192 exists precisely
because one of those internal guards was silently broken for a day.

Migration 193 fixed the ten blood/badge functions by naming `anon` in the
REVOKE. The remaining ~36 migrations have not been swept.

**The sweep is safe to do** — the full set of functions a signed-out visitor
legitimately needs is only eight, derived by grepping every `.rpc(` call
reachable without a login:

| Function | Used by |
|---|---|
| `blood_group_counts` | home page panel, `/blood` |
| `submit_blood_request` | `/blood` request form |
| `homepage_stats` | home page stat cards |
| `public_bill_lookup` | `/water` bill lookup |
| `check_donor_duplicate` | public donation submission |
| `flag_project_comment` | public project pages |
| `project_donation_channels_pkr` | public project pages |
| `project_monthly_sponsorship_pkr` | public project pages |

Everything else in `public` can be revoked from `anon`. Do it as
`REVOKE ... FROM anon` per function (or a `DO` loop over `pg_proc` with the
eight above as an allowlist), then smoke-test all 21 routes under
`src/app/(public)/` — a miss shows up immediately as a broken public page,
not as a silent hole.
